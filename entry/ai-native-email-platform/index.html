Building an Email Platform Where the Interface Is a Conversation with AI

September 2, 2026

The email platform where the entire interface is a conversation with another AI 💬#

Wawai Email Sender is a multi-tenant SaaS for sending email campaigns through Amazon SES. It has no dashboard. The only way to use it is to talk to it, through Claude, ChatGPT, or Gemini, over a protocol called MCP (Model Context Protocol). This is the story of building it solo over about three weeks: the architecture bet, the real production bugs I found along the way, and a couple of bug classes I’d genuinely never seen before, because they only exist when the thing pressing your buttons is a language model.

The problem#

When I started, a tenant’s contacts could live in Airtable, a Google Sheet, or a raw XLSX file someone emailed themselves, and there was no dashboard yet, no auth yet, nothing beyond a plan. The obvious next move for most SaaS products is to build a dashboard. I didn’t, and it wasn’t because I was in a hurry. A few things made a dashboard the wrong first move here:

1. Three incompatible data shapes#

Building a UI on top of Airtable, Sheets, and XLSX would have meant three connector screens before the product did anything useful.

2. The actual user already has a chat window open#

A marketer running one campaign a month doesn’t want to learn a screen for it, they want to describe what they want sent and have it happen.

3. “Green tests” turned out to mean almost nothing on its own#

Every layer of this project, from login to billing, would go on to pass its test suite and still fail the first time it touched real infrastructure. That pattern shows up again and again below.

So the plan became: no dashboard, ever. Every action a dashboard would have offered, previewing a segment, confirming a send, pulling a report, becomes a tool call an AI agent makes on the tenant’s behalf.

The approach#

I built it in layers, and each layer only existed because the one before it created a new problem. Here’s the sketch I drew before any of it was code, the shape everything below still follows:

1. A source-agnostic contact interface#

Before anything else, a DataSourceAdapter interface: one contract, three adapters (Airtable, Sheets, XLSX) behind it, so nothing upstream ever touches a spreadsheet API directly. Everything above this layer just asks for “contacts in this segment” and doesn’t care where they actually live.

2. The interface, as tool calls instead of screens#

Every dashboard action became an MCP tool: preview_campaign, confirm_send, get_campaign_report. A tenant’s AI client calls these directly.

> preview_campaign(tenant_id, segment: "Spring Newsletter")
< 1,204 recipients · preview expires in 15m · preview_hash: a91f…

> confirm_send(preview_hash: "a91f…", subject: "…")
< queued, sent_count updates asynchronously

That meant two server entry points, sharing one implementation (src/mcp/tools.ts): a bare stdio server for local dev with no auth at all, and a hosted server behind real OAuth 2.1 with PKCE, so a real AI client can discover and connect the same way it would any other MCP server. One tool implementation, two doors, so there’s never a second copy of “what a tool does” to drift out of sync with the first.

3. Verify live, not on green#

This one isn’t a code layer, it’s a habit, and it’s the one that ended up mattering most. Every bug story below was caught the same way: by actually running the real path end to end, against real infrastructure, rather than trusting that a passing test suite or a merged PR meant it worked.

A login system that passed every unit test still failed the first time I ran the real authorize → email → verify → token round trip. That gap, between “tested” and “proven,” is where almost every bug in this project actually lived.

What actually broke, and how it got found#

Here’s the part I’d tell another engineer over coffee. Nine real production bugs, all found by watching the real path instead of trusting the tests. A few of the best:

BugWhat the tests saidWhat was actually happeningFix
Login silently brokenAll greenAn object spread let a stale flow_key field clobber the intended one, so no auth-code row was ever written under its real key. Looked exactly like a TTL race.Reorder the spread so the computed key always wins
Real send moved 0 emailsAll greenSQS batch entry IDs used the contact’s raw email address, but SQS only allows [A-Za-z0-9_-] there. Every entry in the batch was invalid.Use the batch-local index instead of the email address
Stuck send, zero log linesAll greenThe MCP SDK validates tool args and routes tool-level errors around our own error middleware, so an early rejection vanished with no trace.Log the raw call before SDK validation runs, not after
Image upload “phantom” failuresAll greenA real photo base64-encodes to 100k+ characters, which hit a model generation-length limit, not a network or server limit.Resize client-side first, add a presigned-URL path for bigger files
Credit gate silently failed in prod121 / 121 greenThe DynamoDB permission was granted to the Lambda’s role but never to the app’s own EC2 role. No test exercises IAM at all.Add the missing policy, then verify from the instance’s own role, not admin creds
Stripe checkout link “incomplete”All greenThe AI client paraphrased a 475-character opaque token while relaying the tool’s output, dropping the trailing # fragment Stripe’s page needs.An explicit “relay this link verbatim, never paraphrased” instruction in the tool’s own response

That last one is my favorite, because it’s not a bug class that could have existed a few years ago.

🐛 The link was byte-exact correct on our side of the wire. I pulled the session straight from Stripe’s own API to check: 475 characters, correct fragment, exactly what their checkout page needs. What the tenant received was ~90 characters with the fragment gone, and session.url had gone from Stripe into the tool’s response untouched, nothing in our code ever modified it.

When the thing executing your product is a language model, “the wire” includes a step where a second model decides how to restate what you handed it. That’s not a step a REST API interface ever needed to account for, and it’s the one bug in this whole project with no real precedent to look up.

Lessons learned#

1. Green tests are a claim, not a proof#

Every one of the bugs above shipped with passing tests. Tests check that the code does what you told it to; they can’t check that what you told it to do is what actually happens against real infrastructure, real IAM roles, or a real AI client’s own quirks. The only thing that closed that gap was running the real path and watching it happen.

2. A tool’s description is the entire onboarding flow#

A dashboard button has a label a human has seen a thousand buttons like before. An MCP tool has a name, a schema, and a description string, and that description is what a model acts on before it ever reads a doc. An AI client once picked the wrong image-upload tool with total confidence, not because it was wrong, but because the description still framed the fragile option as the default. Fixing the sentence fixed the behavior.

3. Ask the human, don’t guess#

A real sent campaign once carried a literal placeholder, “[street address], [city, state zip]”, as its legally-required footer, because nothing forced anyone to fill it in. Anything with a legal or irreversible consequence now fails outright and tells the agent to ask the human for a real answer, instead of quietly shipping a plausible-looking default.

4. Verify from where it runs, not from where you granted it#

121 of 121 tests passing didn’t stop a real IAM gap from breaking credit gating in production, because no test ever exercises IAM. The fix that actually works: check a permission or a secret from the instance that has to use it, not from the admin session that granted it.

Where it stands#

Node.js and TypeScript, the MCP SDK over stdio and Streamable HTTP, Express for a hand-built OAuth 2.1 authorization server, Postgres for tenant data, DynamoDB for campaign state, SQS and Lambda for the send fan-out, SES for delivery, Stripe for billing, all provisioned through Terraform and running on a single EC2 instance behind Caddy. Built, deployed, and operated solo, infrastructure included.

MCP · OAuth 2.1 + PKCE · TypeScript / Node · AWS SES · Lambda · SQS · DynamoDB · Postgres · Stripe · Terraform

Thank you for taking the time to read about this one. If you’re building something where an AI agent is the actual runtime operator, not just a coding assistant, I’d love to hear what bug classes you’ve run into that didn’t exist before.

After all, the interesting bugs are the ones that tell you the rules changed.
